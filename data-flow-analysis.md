# Comprehensive Data Flow & Persistence Architecture Analysis

## 1. Executive Summary

This document details the complete end-to-end audit of data origins, transportation mechanisms, state management, in-memory transformations, and persistence layers across **Everest Textile Mills ERP**.

### Key Findings
1. **Frontend Integration State**: Every page in `frontend/src/pages/*` is connected via the centralized `apiClient` (`api.get`, `api.post`, `api.patch`) pointing to `/api/v1/*`.
2. **Mock Data Isolation**: `frontend/src/data/mockData.ts` was the design source used to seed the initial database schema (`backend/src/db/seed.ts`), but **no frontend page directly imports `mockData.ts`**.
3. **In-Memory Simulations / Hardcoding Discrepancies**:
   - `frontend/src/pages/yarn/YarnInspection.tsx`: Does not store inspection verdicts in the backend. Instead, it reads raw receipts from `GET /api/v1/yarn/receipts` and computes random/synthetic quality defect rates and lot numbers in memory (`(i % 3 === 0 ? 35 : ...)`). Acceptance/rejection decisions are kept strictly in React component state (`records`).
   - `frontend/src/pages/dashboard/Dashboard.tsx`: Hardcoded default fallbacks for KPIs and lag revenue (`1240000`).
   - `backend/src/routes/dashboard.ts` and `machines.ts`: Output today fallbacks to the latest recorded output day if today's date has 0 meters recorded.
4. **Seed Data in Backend**: The initial rows across 14 tables in PostgreSQL were generated by `backend/src/db/seed.ts`, which mirrored `mockData.ts`.
